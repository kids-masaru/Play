# toto（サッカーくじ）予測対戦システム — spec

## 概要

### 何を作るのか（目的・背景）
サッカーくじ **mini toto / toto**（1X2予想 = ホーム勝 / 引分 / アウェイ勝）の予測システムを新規構築する。
位置づけは既存のボートレース「予測対戦」ダッシュボードと**同じ**：

- **目的は「儲ける」ではなく「ユーザー(masaru)の予測眼を育てる学習・比較ツール」**
- 控除率が高く（払戻率約50%）、ROI100%超は構造的に困難という前提を最初から共有する（[[roi_structural_limit]] と同じ構造）
- AI（統計モデル + Gemini）と masaru が並んで予想 → 蓄積 → 結果と答え合わせ → 的中率を比較

### なぜ toto か
- 結果が**3択（ホーム勝 / 分 / アウェイ勝）**だけで、ボートの3連単(120通り)よりモデル化が容易
- Jリーグの試合結果・順位・成績は無料で入手しやすい
- 「なぜこのチームが勝つか」という Gemini の推論が直感的で**教材性が高い**
- 試合は基本週末 → 運用は**週次**でボートより軽い

### 誰が使うのか
masaru 本人（既存ダッシュボードと同じく、学習教材として）。公開URLは既存と同じ。

---

## 技術スタック
- **データ収集**: Python（既存ボートの scraper と同方針：公式サイト等をスクレイピング）
- **保管**: SQLite（`toto/toto.db`）+ CSV（受け渡し用）
- **統計モデル**: Python（v1は Elo + 得点ポアソンで 1X2 確率を算出。将来 LightGBM へ）
- **LLM**: Gemini 2.5 Flash（既存の `GEMINI_API_KEY` を流用）
- **フロント**: 既存ダッシュボードに React タブ追加（`dashboard/src/Toto.jsx`）
- **ユーザー予測の保存**: 既存 Firebase Firestore を流用（[[battle-cloud-sync-firebase]]）。合言葉(uid)も共用
- **公開**: 既存と同じ GitHub → Actions ビルド → gh-pages

## 機能要件（必須機能）

### F1. データ収集（Jリーグ）
- J1/J2/J3 の **日程・結果・順位・直近成績**を取得して `toto.db` に蓄積
- 過去数シーズン分のバックフィル（統計モデルの初期学習用）
- 週次で最新結果を追記

### F2. toto回号の対象試合取得
- toto 公式から、現在販売中の **開催回（回号）** と **対象試合（13試合 / mini は5試合）**・**締切日時**を取得
- 予測はこの「回号の対象試合」を単位に行う

### F3. AI予測（2者）
- **統計モデル（Det相当）**: 各試合の 1X2 確率を算出 → 推奨（H/D/A）
- **Gemini**: 試合情報（対戦・順位・直近成績・ホーム/アウェイ）を渡し、**日本語の推論＋最終予想(H/D/A)**を生成

### F4. ユーザー予測入力
- ダッシュボード「toto」タブで、対象試合ごとに **H / D / A を選択**（ボートの買い目文字列より簡単）
- 自信度・メモは任意。Firebase に保存し複数端末で共有

### F5. 答え合わせ・比較
- 試合終了後、結果を取得 → 各試合の 1X2 を確定
- **統計 / Gemini / ユーザーの的中率**を回号ごと・通算で集計し並べて表示

### F6. 週次フル自動化
- Windows タスクスケジューラ（既存ボートと同方式）で**週次自動実行**：
  1. Jリーグ結果DBを更新
  2. 販売中の回号と対象試合・締切を取得
  3. 統計＋Gemini で予測生成
  4. ダッシュボード用JSON生成 → git push → 公開
  5. 試合終了後、結果取得 → 答え合わせ
- 実装は「毎日軽くチェックし、未予測の開いた回号があれば予測／終了した試合があれば答え合わせ」する冪等なバッチとする（曜日依存の取りこぼし防止）

---

## 非機能要件
- **冪等（idempotent）**: 同じ回号を二重予測しない、結果重複を排除（既存ボートのCSV重複対策と同方針）
- **壊れにくさ**: スクレイピング失敗時もバッチ全体は落とさず警告ログ（既存 morning バッチと同方針）
- **無料枠内**: Gemini は無料枠内（1回号=最大13試合なので呼び出し少）
- **ローカルビルド不可前提**: フロントのビルド検証は push 後の GitHub Actions で（[[windows_build_impossible]]）

---

## やらないこと（スコープ外・v1）
- 海外リーグ対応（Jリーグ中心で確立してから）。※toto回号が海外開催の回は v1 では「対象試合だけ表示、統計予測はスキップ可」とする
- ローカル Gemma 予測（まず統計＋Geminiの2者。動いてから3者目として追加）
- totoGOAL3（得点予想）・WINNER（別種別）
- BIG系（コンピュータ抽選＝予測不可）
- LightGBM 等の高度モデル（v1は Elo+ポアソン。改善は後段）
- 「儲ける」最適化（ケリー資金配分など）。本ツールは学習目的

## 外部連携
- **Jリーグ データ源**: 公式サイト等のスクレイピング（実装時に最終確定：J-League公式/統計サイト）
- **toto 回号・対象試合**: toto 公式サイトのスクレイピング
- **Gemini API**: 既存 `credentials.env` の `GEMINI_API_KEY`
- **Firebase Firestore**: 既存 `boatrace-battle` プロジェクトを流用（toto用に別パス: `users/{uid}/toto/{回号-試合番号}`）
- **GitHub Pages**: 既存デプロイ経路

## 運用フロー（週次イメージ）
```
回号オープン（前節終了後）
  → バッチが対象試合を検知 → 統計＋Gemini予測 → 公開
masaru：締切（土曜の第1試合前）までに H/D/A を入力（好きな端末で）
週末：試合開催
日曜夜〜月：バッチが結果取得 → 答え合わせ → 的中率更新
```

## 備考・制約
- **データのコールドスタート**: 統計モデルは過去データが要る。初回に過去数シーズンをバックフィルするタスクを設ける
- **スクレイピングの脆さ**: 公式サイト改修で壊れうる。失敗時は警告＋スキップで全体は継続
- **toto回号の海外開催**: Jリーグ off-season（12〜2月頃）は海外リーグの回がある。v1では「対象試合の表示とユーザー入力・Geminiは可、統計予測はデータ無ければスキップ」で割り切る
- 既存ボート資産（Firebase同期・ダッシュボード雛形・バッチ/ログ方式）を最大限流用し、新規実装を最小化する

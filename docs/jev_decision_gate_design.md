# Jev判断ゲートの設計・運用ガイド

最終更新: 2026-10-25
状態: 設計確定、現行シャドー運用を維持

## 1. Jevは何をするものか

PlayにおけるJevは、レースをゼロから予測するモデルでも、最終購入を単独で決める責任者でもない。

Jevの役割は、既存モデルが作った候補と構造化された状況を受け取り、短く明確な判断を一貫した形式で返す「二段目の審査役」である。

主な仕事は次の4つに限定する。

1. 候補の中から1つを選ぶ、または選べないと答える。
2. 判断材料が十分かを分類する。
3. 根拠の強さと分散リスクを評価する。
4. 自動処理を続けず、人の確認へ回すべき状況を検出する。

Jevの出力は、的中確率、期待値、真実の証明ではない。特にconfidenceは「回答分布の集中度」として扱い、勝率へ読み替えない。

## 2. なぜ今回うまく見えたのか

2026-10-24確定分までのシャドー比較では、Claudeの候補をJevが1点へ絞った方式は、Claude先頭1点を機械的に買う方式より損失と最大ドローダウンを抑えた。

- Claude先頭1点: ROI 66.1%、収支 -6,880円、最大ドローダウン 7,780円
- Claude → Jev: 56購入、ROI 91.8%、収支 -460円、最大ドローダウン 1,340円

これは「Jevがレースを予測できた」と断定する材料ではない。現時点で支持される説明は、次の組み合わせである。

- 予測そのものはClaudeが担当した。
- Jevへは自由文を大量に渡さず、既存候補、オッズ、モデル一致、直近実績、CLV、データ充足度を構造化して渡した。
- 単一モデル実験では購入可否と候補選択を混ぜず、候補を1点へ絞る狭い質問にした。
- 結果を知らない時点の入力を保存し、同じレースで比較した。
- Jevの判断を実購入へつながず、失敗しても既存処理を止めないシャドー運用にした。

つまり、良かった可能性があるのは「Jevという名前」だけではなく、仕事を狭く定義し、入力と選択肢を整え、結果を後から公平に採点した使い方全体である。

一方、全方式合計ではROI 72.5%であり、`action`による購入可否は382件すべて購入0件だった。したがって、Jevを万能な購入判断者とみなす根拠はない。現状で価値が見えるのは、候補選択とリスク審査である。

## 3. 標準アーキテクチャ

```text
確定ルール・安全条件
        ↓
候補生成（Codex / Claude / 既存モデル）
        ↓
構造化・時系列ガード・入力ハッシュ
        ↓
Jev（選択 / 見送り / 警告 / 人へ回す）
        ↓
シャドー記録
        ↓
結果確定後に採点・同条件比較
        ↓
人が採用可否を判断
```

APIを呼ぶ前に決められる安全条件は、Jevへ任せない。オッズなし、候補不足、未来情報混入、禁止操作などは通常コードのハードルールで止める。

## 4. Jevへ渡す情報

### 必須

- 判断ID、対象時刻、対象日
- 選択可能な候補を固定ID付きで列挙
- 判断に直接必要な構造化特徴
- データ欠損フラグ
- 事前に定義した基準と許される回答
- 前日までに確定した、そのJev実験アーム自身の要約成績
- 入力ハッシュ、質問版、実験版

### Playの場合

- 既存モデルが出した買い目と提案額
- 同じ候補を支持したモデル数
- 予測時オッズ
- 当日事前情報のうち定義済みの数値
- モデルの直近7日・30日成績
- 利用可能ならCLV
- データが揃っているか

### 渡さない

- 対象日当日以降に確定した結果
- 結果を知った後に更新された成績
- モデルの長い説得的な説明文
- 候補外のものを新しく生成させる余地
- APIキー、個人情報、不要な固有名詞
- 「必ず買え」など、回答を誘導する文

## 5. 質問の分け方

一度に複数の目的を混ぜず、必要なら次の判断を分ける。

### 候補選択

- 回答: `candidate_id` または `no_candidate`
- 用途: 既存候補の中から最大1点を選ぶ

### 材料の充足

- 回答: `sufficient` / `insufficient` / `conflicting`
- 用途: 欠損や強い矛盾を検出する

### 根拠・リスク

- 回答: 事前定義した段階値
- 用途: 成績を帯別に検証する。購入確率には使わない

### 緊急確認・人へのエスカレーション

- 回答: `continue` / `hold` / `human_review`
- 用途: セキュリティ警告、不可逆な操作、通常と大きく異なる状態を人へ回す

Playの現行単一モデル比較では、購入可否を混ぜず候補選択へ限定した設計を維持する。全モデルゲートの`action`は購入0件だったため、そのまま本番へ使わず、質問または閾値を別実験として再設計する。

## 6. 出力と監査記録

各判断で最低限、次を保存する。

- `decision_id`
- `occurred_at`
- `experiment_id`
- `experiment_version`
- `question_version`
- `schema_version`
- `input_hash`
- `candidate_ids`
- `decision`
- `confidence`（勝率ではない）
- `data_sufficient`
- `evidence_strength`
- `variance_risk`
- `escalation_reason`
- APIへ要求したモデル名
- API応答で返った正確なモデル名
- エラー種別とフォールバック
- 後日結合する結果、損益、採点日時

自由文の長い理由は監査の補助にとどめ、集計の主キーにしない。

## 7. 新しいJev版を比較する手順

### 原則

- 既存版をコントロール、新版をチャレンジャーとして同時にシャドー実行する。
- 同じレース、同じ時刻、同じ候補、同じ入力JSON、同じ質問、同じスキーマを使う。
- 片方だけに過去結果や追加文脈を渡さない。
- 本番の購入・通知はどちらの回答でも変えない。

### 版の固定

2026-10-25時点のコードは `jev_shadow.py` で `jev-latest` を要求している。`latest`は提供側の更新で中身が切り替わり得るため、厳密な比較のコントロールには使わない。

比較実装時は次を行う。

1. 保存済み応答の`jev_model`で、現在実際に使われた正確な版を確認する。
2. コントロールをその正確な版へ固定する。
3. 新版も正確な版名で指定する。
4. 要求名と応答名の両方を保存し、一致しなければ比較対象外または警告にする。
5. 版が変わった日より前後のデータを、同じアームへ無条件に混ぜない。

### 実験アーム

例:

- `claude_jev_control`
- `claude_jev_challenger`
- `codex_jev_control`
- `codex_jev_challenger`

実験IDには、Jev版、質問版、入力スキーマ版を含める。入力が変わった場合はJev版が同じでも別実験とする。

### 評価

- 同一レースの収支差
- ROIと最大／上位3的中除外ROI
- 最大払戻依存率
- 最大ドローダウン
- 選択一致率、不一致時の成績
- `no_candidate`率
- 欠測率、形式エラー率、応答時間、API費用
- confidence帯別の実績と校正
- ペア・ブートストラップ95%区間

最初の小区間を不具合検出用パイロット、その後を評価用ホールドアウトにする。最低500件までは原則「蓄積中」。採用は自動化せず、人が設計変更の有無と区間推定を確認して決める。

### 採用条件

- 新版が事前に決めた主指標を改善する。
- 95%区間が採用基準を満たす、または十分な件数で少なくとも非劣性を確認する。
- 最大ドローダウン、最大払戻依存率、欠測率のいずれかが許容外に悪化していない。
- 未来情報混入、入力差、版混在がない。
- 本番接続は別途ユーザー承認を得る。

不採用でも結果は保存し、「どの版・どの質問・どの期間で効かなかったか」を次の設計材料にする。

## 8. セキュリティ警告への使い方

Jevは、許可済みの候補から「通常継続」「保留」「人へ確認」を選ぶ補助には向く。ただし、次の処理は通常コードで先に強制する。

- 秘密情報を外へ送らない
- 未知の送信先を拒否する
- 権限不足を拒否する
- 削除、送金、公開、pushなど不可逆操作の承認を要求する

Jevが安全と判定しても、ハードルールを上書きできない。Jevが危険または不明と判定した場合だけ、追加で保留や人の確認へ寄せる。つまり「安全装置を解除するAI」ではなく、「安全装置の手前で異常を拾う審査役」として使う。

## 9. 他のアプリへ転用できる判断

適している例:

- セキュリティ警告の優先度分類と人へのエスカレーション
- 問い合わせ、障害、タスクの担当先振り分け
- 複数のニュース候補から配信候補を選ぶ
- 生成済み返信案を送信候補、要修正、送信禁止へ分類する
- デプロイ候補を実行、保留、人の確認へ分類する

適さない例:

- 事実調査や長文生成そのもの
- 候補の無い状態から創造的な答えを作る仕事
- 正解の定義が曖昧で、評価データも取れない仕事
- 送金、削除、権限付与などを単独で最終承認する仕事

転用時も「候補生成」と「審査」を分離し、まずシャドーで人の判断との差を記録する。

## 10. 実装前チェックリスト

- [ ] 判断目的が1文で言える
- [ ] 選択肢が列挙され、Jevが勝手に追加できない
- [ ] ハードルールを通常コードへ分離した
- [ ] 未来情報と結果漏洩を防ぐ境界がある
- [ ] 正確なモデル版、質問版、入力ハッシュを保存する
- [ ] 比較対象へ同一入力を渡す
- [ ] 判断失敗時の安全なフォールバックがある
- [ ] 実行結果を後から採点できる
- [ ] 本番影響のないシャドー期間がある
- [ ] 採用条件と必要件数を実験開始前に固定した
- [ ] 不可逆操作は人が最終承認する

## 11. Playで次に実装する場合の順序

1. `jev-latest`を、現行応答で確認した正確な版へ固定する。
2. 要求モデル名と応答モデル名を別フィールドで保存する。
3. 新版用のチャレンジャーアームを追加する。
4. 同一入力を両アームへ渡す共通関数とテストを作る。
5. `jev_pairing_performance.py`へ版別のペア比較を追加する。
6. 実験画面へ版、件数、実収支、ストレス指標、95%区間を表示する。
7. 500件までは「蓄積中」とし、実購入へ接続しない。

この順序は準備案であり、本書の作成だけではコードや運用を変更しない。
